# WarpMetal Agent Sandbox

## Objective

Take an existing WarpMetal Agent Runtime sandbox and leave it ready for a
coding agent to work inside it: agent installed and authenticated, GitHub
reachable, repository cloned, workspace prepared.

This skill deliberately does not provision anything. Server, Agent Runtime,
sandbox and per-agent access are somebody else's job, and this file names that
owner explicitly below.

---

## Prerequisites

This skill begins after provisioning has already happened. Do not repeat those
steps here.

For everything up to and including the SSH alias, follow the `warpmetal` skill:
its `SKILL.md` for the flow, and `references/runtime.md` plus
`references/cli-reference.md` for the exact commands. Concretely, that skill
owns:

- WarpMetal CLI version and `health`, `catalog` discovery.
- Server creation or reuse, and Agent Runtime enablement and installation.
- Sandbox creation, including size, lifetime and expiry semantics.
- The per-sandbox Ed25519 identity, the access grant, and its transition to
  `applied`.
- Connection profile materialisation and `sandbox access install-ssh`.

Assert, do not re-derive, the following before continuing:

```text
WarpMetal CLI available, and 0.8.10 or later for sandbox access install-ssh
Agent Runtime healthy
Sandbox running
Grant applied
Host key verified
SSH alias reachable
```

If any of those is not true, stop and hand back to the `warpmetal` skill. A
missing prerequisite is not something to improvise around.

CLI floors: `0.8.1` for WarpMetal generally, `0.8.10` for
`sandbox access install-ssh`.

## Input Parameters

When the user provides these values, preserve them exactly:

```text
agent=<cursor|codex|claude|antigravity|other>
repository=<owner/repository or URL>
sandbox_name=<name>
github_auth=<https|ssh>
```

Minimum required values for this skill:

```text
agent
repository
sandbox_name
```

If `github_auth` was not provided, use HTTPS through GitHub CLI:

```sh
gh auth setup-git
```

Do not ask for tokens or credentials in chat. Authentication must occur inside
the sandbox through the official flow.

---

## Main Rules

1. Always use the official `warpmetal` CLI for WarpMetal.
2. Use `--json` for all WarpMetal commands that support it.
3. Never use the VPS owner key inside the sandbox.
4. Never read, print, copy, or upload private keys.
5. Never open the WarpMetal state file or expose tokens, bootstrap, node
   tokens, payment artifacts, or agent credentials.
6. Keep password, keyboard-interactive, and forwarding disabled.
7. Do not manually modify connection profiles generated by WarpMetal.
8. Do not enable forwarding in an attempt to use Cursor Desktop over Remote-SSH.
9. Ask for confirmation before revoking grants or deleting sandboxes.
10. Stop on an ambiguous status, `manual_review`, `failed`, a different host key
    or an unsupported command.
11. Never invent agent flags or commands.
12. For an unknown agent, consult the official documentation for the installed
    version.
13. Keep agent and GitHub credentials inside the sandbox.
14. Never copy credentials between sandboxes.
15. Do not assume a shared filesystem between sandboxes.
16. Git must be the transfer mechanism between sandboxes.
17. Do not consider the environment ready until all verification gates are
    complete.
18. Do not record secrets in logs, prompts, versioned files, or responses.

## Agent Bootstrap

Detect the installed agent, then install and authenticate it inside the
sandbox through its own official flow.

Read [references/agents.md](references/agents.md) for the per-agent detail:
detection, expected entry point, version check, login, and the documented
interactive and headless modes.

The agent's credentials belong to the sandbox. WarpMetal does not install,
authenticate, configure, or receive credentials for these tools, and neither
does this skill.

---

## Install and Connect GitHub

GitHub access is set up inside the sandbox, never on the host.

Read [references/github.md](references/github.md) for verifying `gh`,
authenticating over HTTPS or SSH, and keeping keys inside the sandbox.

---

## Clone Repository

This step is mandatory for a new sandbox.

After authenticating GitHub, determine the repository URL.

For a GitHub repository expressed as:

```text
<owner>/<repository>
```

use:

```sh
ssh wm-<sandbox_name> 'gh repo clone <owner>/<repository>'
```

For a compatible Git URL:

```sh
ssh wm-<sandbox_name> 'git clone <repository-url>'
```

Enter the workspace:

```sh
ssh wm-<sandbox_name> 'cd <repository-directory> && git remote -v'
```

Verify the remote:

```sh
ssh wm-<sandbox_name> 'cd <repository-directory> && git ls-remote origin HEAD'
```

If the repository requires access and authentication fails, stop.

Do not copy credentials manually.

---

## Prepare Workspace

Inside the repository:

```sh
ssh wm-<sandbox_name> 'cd <repository-directory> && git status'
ssh wm-<sandbox_name> 'cd <repository-directory> && git branch --show-current'
ssh wm-<sandbox_name> 'cd <repository-directory> && git remote -v'
```

Detect the project:

```sh
ssh wm-<sandbox_name> 'cd <repository-directory> && ls'
```

Do not assume the framework, package manager, or test commands.

Detect relevant files:

```text
package.json
pnpm-lock.yaml
yarn.lock
package-lock.json
requirements.txt
pyproject.toml
poetry.lock
Cargo.toml
go.mod
composer.json
Gemfile
```

Run only commands that exist and are appropriate for the project.

Do not modify code during bootstrap unless the user requests it.

## Verification

The sandbox is ready only when every gate passes. Read
[references/verification.md](references/verification.md) for the full checklist
covering the agent, GitHub, the workspace and the security boundaries.

Two notes that matter:

- The infrastructure gates (Runtime healthy, sandbox `running`, grant
  `applied`, host key verified) were asserted on entry and are not re-checked
  here.
- Never declare `READY` for a component whose state is `pending`, `accepted` or
  `unknown`. Report the component and its actual state instead.

Prepare a WarpMetal sandbox for <agent>, connect GitHub,

## Mandatory Stops

Stop and ask for instructions if:

- Runtime is `degraded`, `offline`, or `needs_reinstall`.
- Sandbox is not `running`.
- Grant is not `applied`.
- Host key is missing.
- Host key does not match.
- CLI does not have the required command.
- `manual_review` appears.
- User requests Cursor Desktop over Remote-SSH when forwarding is required.
- Reading a private key is required.
- Reading the state file is required.
- Exposing a token is required.
- Copying a credential is required.
- Repository is not accessible.
- Agent has no known official authentication flow.
- A destructive action is requested without approval.

HTTP `202` or exit code `8` means accepted or pending, not completed.

## Cleanup

For a temporary sandbox, record:

```text
expiresAt
sandboxId
grantId
```

Do not record credentials.

Revoking access early requires approval:

```sh
warpmetal sandbox access revoke \
  --server <serverId> \
  --sandbox <sandboxId> \
  --grant <grantId> \
  --confirm REVOKE \
  --wait \
  --json
```

Deleting the sandbox is irreversible and deletes the workspace:

```sh
warpmetal sandbox delete \
  --server <serverId> \
  --sandbox <sandboxId> \
  --confirm DELETE \
  --wait \
  --json
```

Ask for approval before deleting.

## Expected Result

After bootstrap, the AI agent must be able to run:

```sh
cd <repository-directory>
git status
git remote -v
git fetch origin
```

and access the repository from the sandbox without depending on an external
filesystem.

Expected status:

```text
WarpMetal: READY
Sandbox: READY
SSH: READY
Agent: READY
Agent authentication: READY
GitHub: READY
Repository: READY
Git: READY
Security gates: PASS
Overall: READY
```

If any component fails, report the component and its actual state.

Do not convert `pending`, `accepted`, or `unknown` into `READY`.
